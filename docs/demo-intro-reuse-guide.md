# デモ紹介アニメーションの構造と横展開指示

## この文書の用途

**入口ではない。** 物語の型と、そのデモの紹介構成は先に [docs/demo-intro-design.md](../../docs/demo-intro-design.md) で書く。実装の手順とエンジンは [docs/demo-intro-playbook.md](../../docs/demo-intro-playbook.md) である。本ファイルは **リレー型（型A）** の建設デモを事例にした、複数人端末・書類の移動・カメラ公式の参考である。建設の3役や書類の移動を、人数も画面も違うデモへコピーしてはいけない。秒数・場面数も建設の9場面・約49秒に合わせてはいけない。

CursorやCodexは、設計ルールで見せ切る操作と型（A/B/C）を決めたあと、型Aのときだけこの文書と参照元コードを読む。
参照元は `construction_demo` のトップ画面である。
再生の仕組み（一本の時間、停止、主役最大2枚）は社内ナレッジの `demo-intro/` を基準にする。本ファイルの `CameraStory` を他デモへコピーしない。

2026年9月18日のローカルの作業中コードを確認した。未コミットの変更と未追跡ファイルも含む。
本番サイトやGitHub上のコードとの一致は確認していない。ブラウザでの表示・動作確認も、この文書の作成時には実施していない。
利用時は実装の更新を確認し、行番号ではなくファイル名と関数名で参照する。

## 1. 紹介方法の基本（建設の事例）

見え方の共通規則（主役最大2枚、ズームと2枚並び）は設計ルール側にある。以下は **リレー型（型A）** としての建設の例である。

この紹介はMP4や動画プレイヤーではない。Reactで描いた業務画面とCSSの変形を組み合わせたアニメーションである。

1. 一つの広い舞台に、このデモで実在する端末を置く（建設では担当者ごと）。
2. カメラが端末へ寄り、操作と結果を見せる。同時に光るのは最大2枚。
3. リレー型では、写真や書類が端末間を移動し、業務の受け渡しを見せてよい。
4. カメラが次の主役へ移り、同じ仕事の続きを見せる。
5. 最後に短い文章で成果を示す。3端末を同じ強さで並べて引かない。
6. 紹介の下にあるリンクから、ユーザーが実際のデモへ進む。

横展開では建設の「入力 → 処理 → 確認 → 完了」を共通の段階にしない。見せる操作と段階は設計ルールで、そのデモごとに決める。受け渡しは、人が違うときに限る。
端末数、担当者、場面数は対象業務に合わせる。建設の3役や9場面をそのまま強制しない。
紹介内の画面は見せるための画面とする。ユーザーが操作する本体は、紹介の外に置く。

## 2. トップ画面への組み込み

```text
app/page.tsx
└─ HubView
   ├─ 業種ラベル・タイトル
   ├─ つながると何が起きるかを示す一文
   ├─ CameraStory（紹介アニメーション）
   ├─ 個別デモへの入口カード
   └─ 投資回収・相談へのリンク
```

`HubView.tsx` と `lib/hub.ts` は掲載位置と導線の参考である。
別のサイトへ移植する場合は、紹介部分を既存ページへ追加し、ページ全体を建設デモのハブへ置き換えない。
個別デモへのリンク、相談先、ROIへのリンクは移植先のものを使う。

## 4. 舞台・カメラ・画面の構造

```text
camStoryView（表示窓：幅100%、高さ380px、はみ出しを隠す）
├─ camStorySet（舞台：1100×380px、原点は左上）
│  ├─ 現場スマホ → PhotoSortDemo
│  ├─ 内勤PC → ReportStoryPane
│  ├─ 責任者PC → OpsStoryPane
│  └─ f1・f2・f3（写真・書類・差し戻しの移動物）
├─ camStoryTl（最後の時間の帯。カメラの拡大対象外）
├─ camStoryHud（字幕と場面の印。カメラの拡大対象外）
└─ camStoryHit（再生・停止を受ける透明ボタン）
```

| 端末 | 舞台上の位置と寸法 | カメラの中心の目安 |
| --- | --- | --- |
| 現場スマホ | left 20、top 24、196×338 | 118, 193 |
| 内勤PC | left 250、top 48、360×280 | 430, 188 |
| 責任者PC | left 640、top 48、360×280 | 820, 188 |

`cam: [x, y, scale]` は、舞台上の注目点と倍率を表す。
`camTo()` は次の式で舞台全体を移動する。

```text
表示高さ = max(120, 表示窓の高さ - 62)
移動X = 表示窓の幅 / 2 - 注目点X × 倍率
移動Y = 表示高さ / 2 - 注目点Y × 倍率
transform = translate(移動X, 移動Y) scale(倍率)
```

62pxは字幕のための予約領域である。CSSの時間の帯の下端も62pxを使う。
字幕を長くした場合は、予約領域と字幕の実際の高さを一緒に見直す。
カメラのCSS transitionは1.1秒である。場面の時間には移動中の時間も含まれる。

端末内の画面にも縮小がある。スマホは幅390pxを0.451倍、PCは幅900pxを0.4倍で表示する。
この「端末内の縮小」と「舞台全体のカメラ倍率」を区別する。
端末の位置や寸法を変えたら、カメラの座標、移動物の開始位置と移動量も更新する。

## 5. 台本の契約

現状の `StoryScene` は次の形である。

```ts
type StoryScene = {
  cam: [x: number, y: number, scale: number];
  ms: number;
  text: string;
  css: [delayMs: number, el: StoryEl, phase: string][];
  acts: [delayMs: number, act: StoryAct][];
};
```

- `ms` は場面の長さである。`css` と `acts` の遅延は場面開始から数える。
- `css` は対象要素にクラスを追加する。`isOn` は端末の強調に使う。
- 移動物は `p1` で出現し、`p2` で移動し、`p3` で移動しながら消える。
- `acts` は `runAct()` を通してReactの状態を変更する。
- `play()` は場面ごとに演出クラスを消す。業務画面の状態は次の場面へ引き継ぐ。
- 先頭場面の `reset` が写真・報告書・承認・時間の帯の状態を初期化する。
- 最後の場面が終わると、配列の先頭に戻る。

台本に新しい要素を加えたら `StoryEl` と `elMap()` を更新する。
新しい操作を加えたら `StoryAct` と `runAct()`、対応する画面の状態型を更新する。
字幕の書き換えだけでは業務内容は変わらない。
遅延は場面の長さ未満にし、移動や結果の表示を見せる時間も確保する。
処理ログは現在5件×450msである。ログ数を変えると処理時間も変わる。

## 6. 現在の9場面（合計49秒）

| 順番 | 秒 | カメラ | 見せる変化 | 横展開での意味 |
| --- | --- | --- | --- | --- |
| 1 | 5.6 | 118,193,0.92 | 写真整理を押す → ログ → 分類結果 | 入力が仕事に使える情報になる |
| 2 | 5.6 | 280,190,0.58 | 写真がスマホから内勤PCへ移る | 次の担当者への受け渡し |
| 3 | 6.4 | 430,188,0.9 | 生成ボタン → 作成中 → 下書き | 自動処理によって成果物ができる |
| 4 | 5.2 | 430,188,0.9 | 確認ボタン → 送付用の帳票 | 人が確認して正式な形にする |
| 5 | 6.2 | 640,188,0.52 | 提出 → 書類移動 → 通知到着 | 確認者へ渡る |
| 6 | 5.0 | 820,188,0.88 | 通知を確認した状態になる | 過不足や内容を確認する |
| 7 | 5.6 | 640,188,0.52 | 不足写真の催促 → スマホへ差し戻し | 例外や修正への対応を示す |
| 8 | 4.2 | 820,188,0.88 | 承認ボタン → 承認済 | 仕事が完了する |
| 9 | 5.2 | 530,190,0.38 | 舞台を暗くする → 時間の帯を表示 | 全体の成果をまとめる |

最後は「1件が、その日のうちに終わります。」と16:40・16:55・17:10の時刻を表示する。
これは建設デモの例であり、移植先で裏付けのない時間短縮や効果をそのまま使わない。
9場面・49秒は建設の仕事を見せ切るための長さである。他デモの上限でも下限でもない。
短い紹介が必要なら、単に場面を削除せず、削除した場面が作っていた状態も残りの台本で設定する。見せ切る操作が残るなら、場面を足してよい。

## 7. 業務画面を紹介用に動かす方法

紹介は実際のAPIへ依頼せず、サンプルデータと状態変更で進む。
元コードには保存用の関数もあるが、紹介から保存や送信を行う必要はない。

| 画面 | 入力 | 表示の制御 |
| --- | --- | --- |
| `PhotoSortDemo` | `embed`、`playback` | ログ・処理中・完了・押下を外から渡す |
| `ReportStoryPane` | `phase` | 待機・写真到着・下書き・正式帳票・提出済を切り替える |
| `OpsStoryPane` | `phase` | 到着・確認・催促・承認押下・承認済を切り替える |

移植先でも、既存の表示コンポーネントを使い、紹介専用の薄いラッパーから状態を渡す。
ページ全体を埋め込んでAPIや認証処理を起動しない。
実画面を再利用できない場合は、重要な情報と操作結果を残した紹介用画面を作る。
画面内の文字を全部読ませる必要はない。字幕と強調表示で、何が変わったかを伝える。

## 8. 現状の制約と、移植時に直す事項

以下はソースから確認した事項である。修正済みという意味ではない。

| 現状 | 移植時の指示 |
| --- | --- |
| `stop()` は場面タイマーと場面内イベントを消すが、写真処理用タイマーは消さない | 全タイマーを一元管理し、停止中に処理が進まないようにする |
| `atRef` は再生直後に次の番号になるため、再開すると次の場面へ進む | 一時停止と呼ぶなら残り時間と状態を保持する。簡易方式なら現在場面の先頭から再生し、文言も合わせる |
| CSS transitionやsmooth scrollはタイマー停止だけでは止まらない | 採用する停止仕様に合わせて、移動・スクロールも扱う |
| 写真の完了時にスマホ内を下へスクロールするが、周回時のスクロール初期化がない | 先頭場面でスクロール位置も初期化し、2周目を確認する |
| モーション低減設定は初回に読む。静止表示の分岐ではresize監視を登録しない | 静止表示でもサイズ変更に追従する。設定変更の追従も検討する |
| 画面幅からカメラの平行移動を計算するが、倍率は固定 | 狭い画面の全景と字幕を確認し、必要なら幅に応じた倍率を設ける |
| `--cs-accent` 以外にもオレンジ色の直書きがある | 発光、タップ印、場面の印、端末ラベルも含めて色を揃える |

舞台は `aria-hidden` と `inert` で操作対象から外している。字幕は舞台の外にある。
移植後も、紹介内のボタンへTab移動しないようにする。再生ボタンには状態に合う名前と見えるフォーカス表示を付ける。
モーション低減時は自動再生せず、全体像と説明文を見せる。移植先の子画面の動きやスクロールも止める。

## 9. 移植作業の手順

1. [docs/demo-intro-design.md](../../docs/demo-intro-design.md) で見せ切る操作・焦点・4問・型・場面表を書く。秒数は表の結果であり、先に決めない。設計メモが空ならコードに入らない。実装の入口は [docs/demo-intro-playbook.md](../../docs/demo-intro-playbook.md)。型Aの足し分だけ本ファイルを使う。
2. 移植先のコードと作業ルールを読む。使用技術、掲載場所、既存画面、リンク先を確認する。
3. 選んだ型に合う役割・入力・成果・完了だけを残す。型にない端末は置かない。
4. 場面ごとに「主役（1〜2）・画面で起きること・字幕・秒数」を表にする。
5. 紹介の仕組み、台本、紹介用画面、スタイル、画像を移植先の中に配置する。
6. 移植先の表示コンポーネントを再利用し、台本から状態を渡す。
7. 端末の配置、カメラ、受け渡し演出を、選んだ型に合わせて調整する。リレー型以外では書類の飛び移りを必須にしない。
8. タイマー、再開、周回、静止表示について、前節の制約を解消する。
9. 紹介の下から実際のデモへ進めるようにする。
10. ブラウザで検証し、選んだ型と場面表をREADMEに残す。

React版の配置例は次のとおりである。これは提案であり、現在の抽出済みファイルではない。

```text
components/demo-intro/
├─ DemoIntro.tsx
├─ story.ts
├─ IntroScreens.tsx
├─ DemoIntro.module.css
└─ README.md
```

移植先の規約に合わせて名前や構成を変えてよい。
元の `construction_demo` を別案件向けに書き換えない。コピー後の部品は移植先で管理する。
汎用の設定項目は、実際に差し替える内容に絞る。

## 10. HTML・React・Next.jsでの使い分け

- Next.jsでは、紹介の状態管理とブラウザ操作をClient Componentに置く。ページ全体をClient Componentにする必要はない。
- React／Vite＋Reactでは、紹介の構成を使える。`next/link` などNext.js依存は移植先のリンク方式へ置き換える。`@/` の別名も移植先に合わせる。
- 素のHTML／Vite＋JavaScriptでは、台本とCSSの考え方を使い、JSXとReactの状態管理をDOM更新へ書き換える。TSXはそのまま貼れない。
- 画像の `/images/...` はサイトのルートを基準にする。サブパス配信では、移植先の公開パスに合わせる。
- 専用のアニメーションライブラリは必須ではない。元実装はReact、タイマー、CSS transitionを使う。

## 11. 完了条件

- [ ] 設計ルールの型を1つ選んでおり、型にない端末・担当者が出ていない。
- [ ] 移植先の業務が字幕・画面・変化の3点で一致している。受け渡しはリレー型のときだけ必須。
- [ ] 建設固有の人物、写真、帳票、時刻、URLが意図せず残っていない。
- [ ] すべての画像が表示され、紹介の再生で外部APIや保存処理が実行されない。
- [ ] 360px・390px・768px・デスクトップ幅で、主要な操作結果と字幕を確認した。
- [ ] 最低2周再生し、画面・通知・ログ・スクロールが初期状態へ戻る。
- [ ] 場面移動中と処理中の両方で停止・再開を確認した。
- [ ] ページ離脱と再表示でタイマーやイベントが重複しない。
- [ ] モーション低減時に静止表示が成立し、サイズ変更でも崩れない。
- [ ] キーボードで再生操作ができ、紹介内の装飾画面にはフォーカスが入らない。
- [ ] 実際のデモへのリンクが動き、元のページの操作やスタイルを壊していない。
- [ ] 移植先で必要な型チェック・ビルドが通り、ブラウザに実行時エラーがない。
